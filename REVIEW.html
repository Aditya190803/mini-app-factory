Verdict

The code itself is unusually clean for a project of this kind. No TODOs, essentially no any or @ts-ignore, consistent err instanceof Error handling, request IDs threaded through the main routes, 22 test files, and a CI pipeline that runs typecheck, lint, and tests. I installed dependencies and ran all three: typecheck and lint pass clean, 105 tests pass. That is a real engineering baseline and it is worth saying plainly before the rest.

The problem is not code quality. It is that the entire authorization model is decorative. Every Next.js API route carefully calls stackServerApp.getUser() and then assertCanAccessProject — and every one of those checks can be skipped entirely by talking to Convex directly, because no Convex function authenticates anything. That single fact turns a handful of separate issues into one exploitable chain: OAuth tokens and BYOK API keys sit in plaintext in tables that anyone can read, and generated HTML is served from the app's own origin with no CSP to contain it.

The one-line summary

Fix Convex authorization first. It is the root of four of the five most serious findings, and almost nothing else on this list matters until it is done.

What the product actually is today

Establishing the honest baseline, because the competitive section depends on it.

A prompt and a project name reserve a row in Convex, then /api/generate runs a fixed two-call, non-streaming chain: one generateText call produces a free-text design spec, a second produces the code. Output is parsed out of fenced ```html:index.html blocks by regex. Validation checks exactly one thing — that index.html exists.

The emitted artifact is plain static HTML, hand-written CSS, and vanilla JS. No Tailwind in the output, no framework, no bundler, no package.json, no build step. Pages compose through a custom <!-- include:header.html --> directive resolved at render time. Editing goes through /api/transform, which inlines the whole project into one prompt and asks the model to reply with a bare JSON array of tool calls — not native function calling — which are then applied with cheerio and css-tree. Deploy pushes files one at a time to GitHub and points Vercel or Netlify at the result.

So: a static-site generator with an AI editing loop. Not an app builder. The generated sites have no database, no auth, no server code, and no package ecosystem. Holding that clearly in view is what makes the competitive comparison useful rather than demoralising.

Security · 11 findings

Findings marked verified I confirmed by reading the code directly rather than taking an agent's word for it.

CriticalSEC-1Convex enforces no authorization at all — every API auth check is bypassableverified

Every function in convex/*.ts is exported as a public query or mutation. There is not a single ctx.auth.getUserIdentity(), internalQuery, or internalMutation in the directory — I grepped for all four and got zero hits. Ownership is decided by comparing against a userId string passed in by the caller.

The deployment URL is public by construction (NEXT_PUBLIC_CONVEX_URL), and convex-client-provider.tsx uses a bare ConvexProvider with no auth bridge, so no JWT ever reaches Convex anyway. Anyone can call these directly: integrations.getIntegration returns any user's GitHub, Vercel, and Netlify OAuth tokens; aiSettings.getByUserId returns any user's BYOK API keys; files.saveFiles overwrites or deletes every file in any project; aiSettings.upsertAdminModelConfig rewrites the global admin config, defeating the admin gate entirely; projects.cleanupLegacyFields is an unauthenticated full-table write.

Fix: configure auth.config.ts for Stack Auth JWTs, wire ConvexProviderWithAuth and server-side setAuth(), derive userId from ctx.auth inside every handler, and delete the userId argument from all public signatures. Anything only the Next server should call becomes an internalMutation.

CriticalSEC-2OAuth tokens and BYOK keys stored in plaintext; the encryption secret is declared but never usedverified

lib/env.ts:25 validates INTEGRATION_TOKEN_SECRET at 32+ characters and the README documents it — but it appears nowhere else in the codebase except test fixtures. I grepped every source directory: there is no encrypt or decrypt helper anywhere.

So GitHub tokens land raw in userIntegrations as v.string(), and provider API keys land raw in aiSettings.byokConfigJson. The GitHub OAuth flow requests full scope=repo, meaning read/write on all private repos. Combined with SEC-1, that is direct exfiltration. Disconnecting also only nulls the DB column — no provider revoke call — so a leaked token stays live indefinitely.

CriticalSEC-3Model-generated HTML is served on the app's own origin with no CSP or sandboxverified

/results/<name>/… returns arbitrary generated HTML and JS with a Content-Type header and nothing else. There is no middleware.ts, no headers() in next.config.mjs, and no CSP anywhere in the repo. /results is public — it only checks isPublished.

A script in a published site therefore runs on your origin: it can read localStorage — which is exactly where BYOK keys live under mini_app_factory_ai_byok_v1 — and fetch('/api/…') with the victim's Stack Auth cookies attached. The editor iframe is correctly sandboxed without allow-same-origin, but "Open preview in new tab" does window.open('/preview/…'), escaping that sandbox to the top-level origin.

Fix: serve user content from a separate origin. As a same-day stopgap, add Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups to both routes — the sandbox directive forces an opaque origin, which kills cookie and storage access without breaking the generated site's own JS.

Where to compete

The instinct after reading that matrix is to start adding a database, auth, and integrations. That is the wrong move. Emergent runs a Kubernetes pod per prompt with root access; bolt.new compiled Node to WebAssembly to run in a browser tab; Lovable has ~80 OAuth connectors and pays for third-party pentesting. Those are funded infrastructure bets — Emergent raised at $1.5B. Chasing them produces a worse version of all three.

What is genuinely interesting is that all three share the same top complaint, and it is one this project structurally does not have: unpredictable credit burn. Users of every one of them report paying to fix bugs the agent itself introduced. BYOK plus self-hosting removes that failure mode entirely rather than mitigating it. Lovable additionally cannot import an existing repo at all, and edits one Git branch at a time.

The defensible position

The best self-hosted, bring-your-own-key generator for static marketing sites — landing pages, portfolios, docs, microsites — where no-build output is a genuine feature rather than a limitation. Static HTML deploys anywhere, has no dependency rot, no runtime cost, and perfect Lighthouse scores by default.

That framing makes the roadmap obvious: every reachable-gap row above is worth building, and no structural-gap row is.

Two caveats on scope. First, the README currently claims "production-ready multi-page websites" and lists a hardcoded admin email — both are worth revising against what the tool actually is. Second, the design-quality bar is where these tools genuinely differentiate, and Emergent's own CEO has conceded design as their weakness. A two-call chain with a discarded design spec is leaving a lot on the table there — the spec gets truncated to 500 characters and thrown away.

Sequenced roadmap

Ordered by dependency, not by preference. Each phase unblocks the next.

01

Close the authorization hole

SEC-1 → SEC-4 · blocks everything else · ~1–2 weeks
  • Write the Convex authorization tests first — they are the regression guard (DX-2).
  • Stack Auth JWTs into Convex; derive userId from ctx.auth; delete every userId argument.
  • Demote server-only functions to internalMutation.
  • Ship the sandbox CSP on /results and /preview today; plan the separate origin.
  • Encrypt tokens with the INTEGRATION_TOKEN_SECRET you already validate; stop returning BYOK keys to the browser; delete the dead x-maf-ai-byok header (ARC-1).
  • Escape the favicon interpolation; add ownership to updateMetadata.
02

Stop losing user work

BUG-1, BUG-2, BUG-5, BUG-7, ARC-6 · ~1 week
  • Add filesVersion with optimistic concurrency — fixes the wipe race and the transform/autosave collision in one change.
  • Stop persisting previewHtml as project.html; retire the legacy mirror.
  • Make name reservation atomic inside the mutation.
  • Cascade deletes across projectFiles, editHistory, deploymentHistory.
  • Give deploy a maxDuration and a single Git Data tree push.
  • Quick wins while in here: the ZIP README key, the Delete-key shortcut, testTimeout, !.env.example.
03

Make the agent loop competitive

The highest product leverage on this list · ~3–4 weeks
  • Error feedback loop. On tool failure, collect {tool, args, error} and send one repair turn instead of aborting. Cap at two rounds. This alone closes the largest single quality gap.
  • Capture runtime errors. Add window.onerror, unhandledrejection, and a console proxy to the preview bridge; surface them in the sidebar with a one-click "fix this" that includes the stack.
  • Native tool calling. lib/ai-tools.ts already has the schemas and is unused — switching deletes 167 lines of JSON extraction plus the repair round-trip.
  • Multi-turn sessions. Keep the last N turns per project so "no, smaller" works.
  • A real validator. Link, anchor, and asset resolution plus cheerio/css-tree parse checks, fed back for one automatic repair pass before reporting success. Today validation checks one filename despite ~40 lines of prompt text demanding link integrity.
  • Stream generation. ai-client.stream() and parseStreamingOutput are already stubbed; delete the 1.6 s of fake progress.
  • Token-aware budgeting instead of a character cap — and never truncate a primary file mid-content, which currently hands the model broken HTML to edit.
04

Reach editor parity

The reachable-gap rows · ~3 weeks
